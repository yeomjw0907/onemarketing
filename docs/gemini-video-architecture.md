# Gemini 영상 분석과 제작 개선 아키텍처

작성일: 2026년 11월 3일

상태: 구현 전 설계안. API 호출, DB 변경, 영상 수집은 실행하지 않았다.

후속 기록: 이 문서는 최초 설계 시점의 상태를 보존한다. 2026년 11월 3일 로컬 연구소 MVP와 30개 영상 API 시험을 진행했다. 현재 구현 범위와 운영 통합 전 남은 작업은 `docs/clip-lab.md`를 따른다.

## 결정

Gemini를 영상 분석 공급사로 추가한다. 참고 영상에서 시간대별 연출을 추출하고, 확인한 지식을 장면 계획에 반영한다. 생성 결과도 같은 분석기로 검사한다. 기존 영상 생성 공급사와 더빙·자막 처리는 유지하면서 장면별 제작을 확장한다.

첫 구현은 공개 YouTube 링크 또는 권한이 확인된 업로드 영상 한 개를 분석해 검토 가능한 기록으로 저장하는 데 한정한다. 자동 탐색, 2,000개 분석, 자동 재생성은 후속 단계다. Playwright는 필수 구성 요소가 아니다.

## 확인한 코드와 환경

- `src/lib/providers.ts`: 이미지 한 장을 기준으로 fal 영상 생성을 요청한다. 혼합형은 생성 영상 한 개를 `hybrid()`로 넘긴다.
- `src/lib/video.ts`: 정지 이미지 클립 연결과 생성 영상 한 개 뒤에 이미지들을 연결하는 경로가 있다. 임의의 여러 생성 장면을 관리하는 타임라인은 없다.
- `src/lib/media-plans.ts`: 장면 설명 배열은 있지만 생성 기준 이미지·프롬프트·설정은 계획 전체를 중심으로 묶인다. 장면 배열의 존재가 장면별 생성 실행을 의미하지 않는다.
- `src/lib/jobs.ts`, `worker.ts`: 작업 lease, 재개, 비용 불확실 상태를 관리한다. enqueue와 claim은 프로젝트 및 프로젝트 단계에 결합되어 있다.
- `src/lib/ai-cost-ledger.ts`: Claude 사용량 추정과 fal 청구 확인 중심이다. Gemini 사용량을 기록하는 것만으로 비용 화면에 정확하게 반영되지는 않는다.
- `src/lib/db.ts`, `types.ts`: PostgreSQL의 `records`에 kind별 JSON 문서를 저장한다. `assets.ts`는 비공개 파일 저장을 사용한다.
- 복제본의 `src`, `scripts`, `.env.example`에서는 Gemini 연동을 찾지 못했다. 로컬 `.env.local`도 없다. 운영 키가 있다는 사용자 설명을 전제로 하되 키의 실제 환경변수 이름, 공급사 계정 방식, 접근 가능한 모델은 구현 시 확인한다. 키 값은 출력하거나 문서에 기록하지 않는다.

## 처리 흐름

1. 관리자가 참고 링크 또는 보유 영상 자산을 등록한다.
2. 서버가 권한, 입력 형식, 중복 여부와 예산을 확인한다.
3. 분석 작업을 만들고 워커가 Gemini에 영상 입력을 전달한다.
4. 구조화된 장면 분석을 애플리케이션에서 다시 검증한다.
5. 필요한 구간만 정밀 분석하고, 관리자가 근거와 해석을 검토한다.
6. 검토한 기록에서 연출 규칙을 추출한다.
7. 장면 계획 작성 시 적용 조건에 맞는 규칙을 검색한다.
8. 장면별 생성과 편집 후 최종 영상을 검사하고 실험 결과를 기록한다.

이 흐름의 학습은 지식 검색과 제작 피드백의 누적이다. 기반 모델의 가중치를 자동으로 학습시키는 구조가 아니다.

## 모듈 경계

아래 파일 이름은 추가 제안이며 아직 구현하지 않았다.

- `gemini-client.ts`: 서버 전용 인증, 모델 설정, 요청 제한 시간, 응답·사용량 정규화. 영상 분석 외 기능에서도 재사용할 수 있다.
- `video-analysis-schema.ts`: Zod 분석 스키마, 타임스탬프·참조·길이 검증. 공급사가 지원하는 JSON Schema 부분집합으로 변환한다.
- `video-analysis.ts`: 영상 입력 준비, 전체 분석, 선택 구간 재분석, 결과 버전 관리.
- `video-analysis-jobs.ts`: 참고 자료 분석 등록, 예산 예약, 중복 방지, 재시도 판단. 고객 제작용 enqueue를 우회 호출하지 않는다.
- `video-knowledge.ts`: 검토한 연출 규칙의 등록·검색·폐기와 출처 연결.
- `video-quality.ts`: 생성 영상과 장면 계획을 비교한 검사 결과. 참고 영상의 연출 분석과 출력 스키마를 분리한다.
- `video-timeline.ts`: 장면별 자산 선택, trim, 화면·소리 타이밍, 출력 규격 정규화와 조립.

`providers.ts`의 기존 영상 생성 함수를 분석 함수로 대체하지 않는다. 분석, 계획, 생성, 검수는 서로 다른 입력·출력과 비용을 가진다.

## 영상 입력

공개 YouTube는 Gemini의 영상 입력 기능에 URL을 전달한다. 일반 웹 페이지의 URL context나 자막 텍스트만을 영상 입력의 대체재로 취급하지 않는다. 링크는 video ID로 정규화하고 shorts, watch, youtu.be 형식 간 중복을 제거한다.

업로드 영상은 기존 비공개 자산의 접근 권한을 검사한 뒤 서버에서 읽어 Gemini File API로 전송한다. 공급사 파일 ID, 처리 상태와 만료 정보를 저장하고 작업 종료 후 삭제를 예약한다. 비공개 자산을 공개 URL로 바꾸지 않는다.

링크 접근 실패, 삭제, 비공개, 지역 제한, 분석 거절은 별도 결과로 기록한다. 제목과 설명만 보고 영상 분석이 성공했다고 표시하지 않는다. 분석할 수 없는 링크를 임의 다운로드로 우회하지 않는다.

정밀 분석은 공급사의 지원 범위를 확인한 구간 지정·샘플링 설정을 우선 사용한다. 직접 보유한 원본에는 FFmpeg로 구간과 프레임을 추출할 수 있다. 추출한 이미지만으로 소리와 움직임을 확인했다고 주장하지 않는다.

## 데이터 모델

초기에는 기존 `records` 저장 방식을 따른다. 아래 kind를 추가하고 `types.ts`, 서버 권한 검사, 삭제·내보내기 경로를 함께 갱신한다. 고객 화면에 전부 내려가는 DatabaseView에는 원본 분석을 자동 포함하지 않는다.

- `video_references`: scope, ownerId, projectId(선택), 정규화 URL/video ID 또는 asset ID, 원본 해시(보유 파일), 길이, 언어, 업종, 목적, 권리 근거, 등록자, 접근 상태.
- `video_analysis_runs`: referenceId, 입력 식별자, model, provider API 버전, promptVersion, schemaVersion, 설정, 관측 시점, 처리 상태, 원본 응답의 비공개 저장 위치, 검증 오류, 결과 요약, 검토 상태.
- `video_analysis_segments`: runId, startMs/endMs, 장면 역할, 화면·동작·카메라·자막·소리 관찰, 확인하지 못한 항목, 근거와 정밀 분석 참조.
- `video_patterns`: 적용 조건, 연출 지침, 금지 조건, source segment IDs, ruleVersion, 검토자, evidenceLevel, 활성·폐기 상태.
- `video_experiments`: 비교 대상 제작 버전, 대본·더빙 식별자, 적용 pattern 버전, 계획 버전, 생성 설정, 비용, 사람 평가, 게시 지표와 관측 시점.

scope는 `internal_library`와 `project`를 구분한다. 내부 공통 라이브러리는 권한 있는 관리자만 운영한다. 고객 자료와 그로부터 추출한 규칙은 기본적으로 프로젝트 범위에 머문다. 공통 전환은 별도 권한과 검토 이력을 요구한다.

공개 성과는 분석 모델이 추측하지 않도록 별도 snapshot으로 저장한다. 조회수·좋아요·댓글은 값, 출처, 확인 시점, 누락 여부를 갖는다. 시청 유지율 등 소유자 전용 지표와 섞지 않는다. 자동 공개 지표 수집은 후속 어댑터이며 첫 구현에는 필수가 아니다.

2,000개 조회를 `list()`로 전부 읽지 않는다. scope, referenceId, status, createdAt으로 제한한 커서 페이지 조회를 사용한다. 중복 식별자와 작업 key에 DB 유일성을 보장하고 조회 패턴에 맞는 인덱스를 추가한다. 실행 가능한 SQL과 마이그레이션은 구현 단계에서 확정한다.

## 분석 출력 계약

모델 출력은 다음 정보를 갖는 구조화된 JSON으로 받는다.

- `inputCoverage`: 화면·소리·자막 각각 observed / unavailable / uncertain, 분석한 시간 구간, 샘플링 설정. 이는 모델의 자기 보고이므로 별도 확인 자료가 필요하다.
- `segments`: 밀리초 단위 시작·끝, 역할, 화면 설명, 피사체 행동, 카메라 이동, 전환, 화면 자막, 소리 이벤트. 확인하지 못한 값은 null 또는 unavailable로 남긴다.
- `observations`: 실제 관찰한 사실과 segment 참조.
- `hypotheses`: 효과에 대한 해석, 대안 설명, 확인할 실험. 성공 원인을 사실처럼 출력하지 않는다.
- `reproduction`: 생성에 필요한 시작 상태, 행동, 종료 상태, 연속성 조건, 이미지·생성 영상·실사 중 적합한 제작 방식.

서버는 0 <= startMs < endMs <= 확인된 영상 길이, 시간 순서, 근거 참조 존재, 문자열·배열 크기와 스키마 버전을 검사한다. 장면 구간은 겹치지 않게 하고 소리·자막 이벤트는 겹침을 허용한다. 길이를 확인하지 못하면 lengthUnverified로 남기고 승인된 제작 규칙으로 자동 승격하지 않는다.

모델 거절, 빈 응답, 출력 잘림, 스키마 오류를 구분한다. 공급사 JSON 형식 준수는 내용의 정확성을 보장하지 않는다. 미세한 컷 시점은 검토 전까지 근사값이다.

영상 속 자막·음성·댓글은 분석 대상 데이터다. 그 안의 명령을 시스템 지시로 실행하지 않으며 분석 모델에 도구 실행이나 비밀 조회 권한을 주지 않는다.

## 작업 큐와 비용

작업 type 제안은 `video-analyze`, `video-analyze-detail`, `video-pattern-extract`, `video-quality-review`다. 후속 제작 단계에서 `video-shot-generate`, `video-assemble`을 추가한다.

기존 lease와 로그 개념은 공유하되 scope별 등록·예산 정책을 분리한다. 현재 claim은 프로젝트 존재와 단계를 검사하므로 type만 추가해서는 공통 라이브러리 작업이 실행되지 않는다. `scopeType/scopeId`를 명시한 claim 분기를 추가하고 기존 제작 작업은 기존 project 정책을 그대로 적용한다. 임의의 가짜 고객 프로젝트로 공통 분석 비용을 청구하지 않는다. 비용 화면도 내부 연구 비용과 고객 제작비를 구분한다.

작업 상태는 기존 pending/running/succeeded/failed/uncertain을 활용한다. 상세 stage는 validate, prepare_input, analyze_overview, validate_result, analyze_detail, persist_result, awaiting_review로 별도 관리한다. awaiting_review는 API 작업의 running 상태가 아니다. 분석 완료와 사람 검토 완료를 분리한다.

중복 key는 scope, video ID 또는 원본 해시, 입력 revision, model, prompt/schema 버전, 분석 구간, 설정의 해시로 만든다. 완료 결과는 재사용한다. YouTube ID는 콘텐츠 해시가 아니므로 관측 시점과 명시적 재분석 revision도 저장한다.

호출 전에 attempt와 예산 예약을 저장한다. 호출 후에는 실제 사용량, provider request ID(제공되는 경우), 응답 저장 위치를 체크포인트로 남긴다. 결과와 완료 상태는 트랜잭션으로 저장하며 완료된 단계는 다시 호출하지 않는다.

Gemini 요청이 fal처럼 항상 나중에 조회 가능한 작업 ID를 준다고 가정하지 않는다. 응답 수신 전 연결이 끊기면 uncertain으로 두고 자동 재호출하지 않는다. lease 만료도 attempt 전송 상태로 판단한다. 외부 호출의 정확히 한 번 실행을 보장한다고 표현하지 않는다. 확실하게 미전송인 실패만 제한적으로 재시도하고 429는 Retry-After와 계정별 속도 제한을 따른다.

첫 단계는 전용 워커에서 한 번에 한 개를 분석한다. 계정의 실제 quota와 지연을 측정한 뒤 동시성을 올린다. FFmpeg 구간 추출은 전용 워커에 배치한다. 서버리스 실행은 API 응답 시간을 포함해 예산 안에 완료 가능한 단계만 맡긴다.

Gemini 사용량 원본과 가격표 버전을 저장하고 `ai-cost-ledger.ts`에 Gemini 계산 경로를 추가한다. 추정액과 청구 확정액은 구분한다. 가격이나 사용량을 모르면 0원이 아닌 미확인으로 표시한다. 일일·실행별 상한은 대기 작업의 예약액도 포함해 원자적으로 검사한다. 취소는 다음 호출을 막으며 이미 전송된 비용을 되돌렸다고 표시하지 않는다.

## 키와 데이터 접근

기존 운영 키의 설정 위치와 환경변수 이름을 먼저 확인한다. 제안 설정명은 GEMINI_API_KEY, GEMINI_VIDEO_ANALYSIS_MODEL, GEMINI_VIDEO_DETAIL_MODEL이다. 모델 이름은 하드코딩하지 않고 실제 키의 접근 권한과 영상·구조화 출력 지원 조합을 소규모 시험한다. 프런트엔드로 키를 보내지 않는다.

기존 `redactLog()`의 비밀 목록에 실제 Gemini 환경변수 이름을 추가한다. 요청 헤더, 원본 응답, signed URL, 공급사 업로드 주소를 일반 로그에 남기지 않는다.

서버는 모든 reference/run/segment/pattern/job 요청의 scope와 프로젝트 접근 권한을 확인한다. 현재 서버의 PostgreSQL 접근은 소유자 권한이므로 RLS만으로 프로젝트 분리를 기대하지 않는다. 기존 records RLS·권한 제한을 유지하고 새 저장소도 직접 Data API에 노출하지 않는다. 원본 응답과 공급사 임시 파일은 제한된 보관 기간과 삭제 상태를 갖는다. 보관 기간은 구현 배포 전 운영 정책으로 확정한다.

## 지식을 장면 생성에 연결

초기 검색은 업종, 목적, 영상 길이, 인물·손 등장 여부, 제작 가능 방식으로 필터링한다. 승인된 규칙만 가져오고 evidenceLevel을 함께 보여준다. 처음부터 벡터 DB를 추가하지 않는다. 검색 실패 사례가 쌓이면 임베딩 검색을 평가한다.

연출 규칙은 candidate → reviewed → tested로 관리한다. 반복 관찰은 tested의 조건이 아니다. 내부 제작 비교 결과가 연결되어야 tested가 된다. 삭제·비공개된 출처는 검토 필요 상태로 바꾸고, 기각된 분석을 참조하는 규칙은 신규 계획 검색에서 제외한다.

미디어 계획에는 적용 pattern ID/버전과 다음 장면 필드를 추가한다.

- shotId, narrationStartMs/narrationEndMs, timelineStartMs/timelineEndMs
- 기준 이미지 asset/version, 공통 인물·제품 제약, 시작·종료 상태
- 장면별 prompt, 생성 길이, 사용할 trim 범위, 모델·설정
- 이전/다음 shot 연결 조건, 전환 종류와 겹침 길이

더빙의 실제 타이밍이 기준이며 평균 길이로 나누지 않는다. 계획 생성 시 더빙 버전과 hash를 고정한다. 더빙이 바뀌면 연결된 계획과 검수를 오래된 상태로 표시한다. 승인된 계획 변경은 새 버전과 예산으로 재승인한다.

장면별 생성은 독립된 자산과 비용을 갖는다. 모델의 최소 생성 길이보다 짧은 장면은 길게 생성한 뒤 사용할 구간을 선택한다. 모델이 종료 프레임 제어를 지원한다고 가정하지 않는다. 연속성 보장이 어려우면 공통 기준 이미지, 동작 방향 제약, 의도적인 컷으로 대체한다.

조립은 장면별 해상도·FPS·코덱·색상·오디오 유무를 정규화한 뒤 수행한다. 전환 겹침을 포함한 타임라인 길이를 실제 더빙 길이와 맞춘다. 먼저 화면을 조립하고 더빙·음원·자막을 한 번 합성한다. 현재 decorateVideo의 오디오 제거 동작을 고려해 기존 경로와 중복 합성을 피한다.

## 생성 결과 검수

계획과 완성 영상을 함께 입력해 제품·인물 일관성, 행동 완료, 깜빡임·변형, 연결, 더빙 의미 일치, 자막 가독성을 검사한다. 출력은 shotId, 구간, 심각도, 관찰, 확인 필요 여부, 수정 제안으로 구성한다.

영상 길이, 해상도, 무음 여부 같은 항목은 FFprobe/FFmpeg로 측정한다. AI 판단과 측정 결과를 구분한다. AI 점수만으로 자동 공개하거나 무제한 재생성하지 않는다. 초기에는 관리자가 문제 장면과 예상 추가 비용을 확인해 장면별 재생성을 요청한다.

## 관리자 기능과 API 제안

- 참고 영상 등록, 분석 요청, 진행 상태와 비용 보기.
- 원본 링크와 시간대별 분석을 나란히 확인하고 관찰 수정·승인·기각.
- 규칙의 근거 영상과 실험 결과 조회.
- 미디어 계획에서 규칙 선택과 적용 이유 확인.
- 검수 결과에서 문제 장면만 다시 생성.

신규 API 제안은 POST/GET `/api/video-references`, POST `/api/video-references/:id/analyses`, GET `/api/video-analyses/:id`, POST `/api/video-analyses/:id/review`, GET `/api/video-patterns`다. 생성 요청은 사용자 명령 key와 scope를 필수로 받는다. 관리자 인증과 scope 검사는 서버에서 수행한다. 모델 이름, 프롬프트 버전 같은 운영 정보는 관리자 상세에 두고 고객의 기본 작업 흐름에 노출하지 않는다.

## 구현 순서와 완료 기준

### 1단계 영상 한 개 분석

Gemini 어댑터, 스키마, 작업 분기, 저장·검토 화면, 비용 기록, 비밀 마스킹을 구현한다. 공개 링크와 권한 있는 업로드를 각각 시험한다. 실제 API 시험 전 키의 설정과 지출 상한을 확인한다.

통과 조건: 화면과 소리가 입력되었는지 확인할 수 있고, 스키마·시간 검증을 통과하며, 잘못된 URL·거절·응답 잘림·불확실한 전송을 성공으로 처리하지 않는다. 같은 요청을 다시 보내도 완료 작업을 재호출하지 않는다. 다른 프로젝트 자료를 읽거나 분석할 수 없어야 한다.

### 2단계 10개에서 50개로 분석 기준 검증

화면·자막·소리·빠른 전환이 있는 영상을 포함해 사람이 확인한 구간과 비교한다. 시험 표본은 규칙 개선용과 별도 평가용으로 나눈다. 장면 경계 오차, 관찰 오류, 소리 이벤트 누락, 사람 수정 시간, 비용, 처리 시간을 기록한다. 모델 자기 신뢰도를 정확도 수치로 쓰지 않는다.

확대 기준 제안: 별도 평가 영상에서 핵심 장면 관찰 정확도 90% 이상, 장면 경계 중앙 절대 오차 0.5초 이하, 중대한 관찰 오류 없음. 이는 달성 결과가 아닌 초기 목표다. 사람이 허용 오차를 확정하고 실제 수치에 따라 샘플링과 비용을 조정한다.

### 3단계 규칙 검색과 장면별 제작

검토한 규칙을 장면 계획에 연결하고 장면별 생성·조립·검수를 구현한다. 동일 대본·더빙의 현재 방식과 개선 방식을 5쌍 비교한다. 제작 방식을 숨긴 평가로 제품 이해도, 자연스러움, 시청 의향, 치명적 결함, 비용과 제작 시간을 비교한다.

### 4단계 200개에서 2,000개로 확대

업종과 채널 쏠림을 제한하고 보통 성과의 비교 영상을 포함한다. 배치별 예산, 실패 격리, 속도 제한, 재개, 취소를 검증한 뒤 확대한다. 높은 조회수와 연출의 인과관계를 단정하지 않는다. 실제 게시 성과는 계정 소유자가 제공한 지표로 별도 검증한다.

## 검증 항목

구현 시 의미 있는 자동 검증은 URL 정규화와 중복, 시간 범위·참조 검증, 프로젝트 권한, 원자적 예산 예약, 중복 enqueue, lease 만료 후 불확실 전송, 업로드 만료와 삭제, 비용 미확인 처리에 집중한다. 공급사 응답을 재현한 테스트를 기본으로 하고 실제 유료 호출은 작은 통합 시험으로 분리한다. 이후 더빙 변경에 따른 계획 무효화, 실패 장면만 재생성, 전환 겹침 후 전체 길이와 음성 유지까지 end-to-end로 확인한다.
