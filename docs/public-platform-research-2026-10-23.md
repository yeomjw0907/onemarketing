# 광고주 상품 신청·체험단 공개 모집 플랫폼 조사

조사일: 2026-10-23 (한국 시간)

## 요청과 조사 범위

광고주는 마케팅 상품을 선택하고 신청하며, 체험단은 운영자의 추천 제안을 받는 동시에 공개 캠페인에 직접 지원할 수 있어야 한다. 두 경로 모두 기존 관리 시스템에 연결한다.

사용자가 먼저 타 플랫폼을 충분히 조사하고 돌아오라고 요청했으므로, 이 문서는 조사 결과와 구현 기준이다. 이 단계에서는 서비스 코드를 변경하거나 새 기능을 배포하지 않는다.

공식 공개 페이지·이용 가이드와 실제 브라우저 화면을 조사했다. 외부 서비스에 회원가입하거나 문의·캠페인 신청·결제는 하지 않았다. 로그인 후 전용 화면의 동작을 직접 검증한 것으로 해석하지 않는다. 경쟁사의 홍보 수치·성과 주장은 검증된 성과로 인용하지 않는다.

## 우리 서비스에 적용할 결론

광고주에게는 상품을 직접 선택하는 경로와 맞춤 상담 경로를 함께 제공한다. 체험단에게는 공개 지원과 개인 추천 제안을 함께 제공한다. 상품 신청·모집·배정·제작·정산을 별도 서비스로 나누지 않고 기존 프로젝트에 연결한다.

우리의 현재 상품은 원마케팅이 원고·이미지·영상을 제작하고 참여자가 확인 후 게시하는 방식이다. 일반적인 방문·제품 체험 후 리뷰 작성과 구분해서 상품 설명과 캠페인 상세에 표시한다. 실제 체험이 필요한 상품을 추가하면 별도 유형으로 취급한다.

## 광고주 화면과 운영 흐름

상품 목록 → 상세·구성 선택 → 예상 금액 확인 → 브랜드·제품 정보 입력 → 신청 접수 → 운영자 확인·견적 확정 → 제작·모집·게시 진행 → 결과 보고

1. 초기 상품은 현재 지원하는 블로그, 클립, 블로그+클립 묶음으로 구성한다.
2. 상품마다 제공 결과물, 수량 단위, 일정 기준, 수정 범위, 포함/추가 비용을 표시한다.
3. 광고주 판매가와 참여자 원고료는 서로 다른 값이다. 내부 보수·AI 원가·마진은 공개하지 않는다.
4. 단가는 기존 가격 관리와 연결하되, 공개 상품 여부와 공개 설명은 명시적으로 관리한다.
5. 신청 당시 상품·판매가·수량·조건을 저장한다. 관리자 가격 변경으로 접수된 신청 금액을 조용히 바꾸지 않는다.
6. 브랜드명·연락처·상품 URL·목표·희망 일정 등으로 접수하고, 작업에 필요한 상세 자료는 후속 단계에서 보완한다.
7. 고객/제품 연결과 견적 전환은 한 번만 실행한다. 이름이나 같은 회사명만으로 다른 계정의 고객 데이터에 연결하지 않는다.
8. 광고주 마이페이지에서 내 신청, 보완 요청, 견적/진행 상태, 게시 결과 링크를 확인하게 한다.
9. 결제 방식은 현재 미확정이다. 첫 버전은 실제 신청·견적·입금 확인 흐름으로 연결하고, 결제 완료처럼 보이는 가짜 화면은 만들지 않는다. 온라인 결제는 PG·취소 정책까지 함께 정해 붙인다.

## 체험단 공개 모집과 기존 추천 제안의 연결

공개 캠페인 목록 → 상세 조건 확인 → 회원 로그인·활동 계정 선택 → 지원 → 운영자 선정 → 참여 조건 최종 수락 → 기존 게시 작업 화면

1. 공개 모집은 프로젝트를 기준으로 묶고 블로그/클립/묶음 모집 유형을 표시한다. 내부 개별 슬롯마다 같은 제목의 공고를 반복 노출하지 않는다.
2. 목록에서 원고료, 채널, 모집 마감, 게시 마감, 제공 콘텐츠 여부를 비교할 수 있게 한다.
3. 상세에서 실제 수행할 일, 제출물, 게시 유지 조건, 지급 조건, 신청 가능한 활동 계정을 안내한다.
4. 캠페인 지원과 최종 배정은 별도 상태다. 회원 자동 승인이 캠페인 자동 선정으로 이어지지 않는다.
5. 지원 기록은 누가 어떤 계정·조건으로 지원했는지 남기고, 선정 시 기존 제안·수락 엔진에 연결한다.
6. 직접 지원자와 추천 후보는 같은 모집 화면에서 비교하되, 유입 경로를 구분해 표시한다.
7. 운영자의 개인 추천 제안은 현재 기능을 유지한다. 공개 지원 여부가 기존 제안·수락 기록을 덮어쓰지 않는다.
8. 동일 회원·캠페인의 중복 지원을 막고 기존 제안이 있으면 해당 제안으로 안내한다. 같은 계정·채널의 중복 작업은 기존 검사를 재사용한다.
9. 모집 가능 수량은 진행 중인 제안의 예약·만료·수락과 최종 배정을 함께 반영한다. 지원 버튼을 누르는 것만으로 슬롯을 소진시키지 않는다.
10. 보류·종료·취소·마감한 캠페인의 신규 지원은 서버에서도 차단한다.
11. 모집 공개는 운영자가 승인한 정보만 대상으로 한다. 내부 프로젝트 생성이 곧 대외 공개를 뜻하지 않는다.
12. 참여자 마이페이지는 추천받은 제안, 내가 지원한 캠페인, 선정 후 게시 작업을 구분한다.
13. 기존 원고료와 추천 보상은 기존 지급 흐름에서 계산한다. 지원·선정만으로 특별 보상을 발생시키지 않는다.

## 첫 구현 범위

- 광고주: 공개 상품 목록·상세, 수량/구성 선택, 신청서, 내 신청·진행 내역.
- 참여자: 공개 캠페인 목록·상세, 계정 선택 후 지원·철회, 내 지원 상태, 기존 추천 제안 유지.
- 운영자: 광고 신청 접수함, 기존 고객/제품 연결과 견적 전환, 캠페인 공개/마감, 지원자와 추천 후보 비교·선정.
- 공통: 역할별 서버 권한, 신청 재전송·선정 동시성 처리, 기존 정산·리포트 연결, 모바일 검증.

초기에는 현재 운영 중인 블로그·클립 상품에 집중한다. 대행사 입점·입찰, 범용 상품 판매, 유료 노출, 커뮤니티는 이 두 신청 흐름이 안정된 뒤 별도 판단한다.

## 화면 원칙과 구현 순서

광고주와 참여자의 입구를 분명하게 나누고, 광고주에게는 판매 구성·총액·신청, 참여자에게는 수행 조건·원고료·기한·지원을 우선 배치한다. 기존 운영 화면의 한 가지 강조색과 타이포그래피를 이어간다.

1. 공개용 상품/캠페인 데이터와 신청 원장, 권한·상태 전이를 먼저 정의한다.
2. 광고주 상품 선택·신청과 운영자 접수함을 연결한다.
3. 공개 모집·체험단 지원과 기존 추천/제안/수락을 연결한다.
4. 광고주 내 신청·진행 내역과 기존 결과 보고를 연결한다.
5. 실제 상품 게시 → 광고 신청 → 견적 전환 → 캠페인 공개 → 지원·추천 → 선정·수락 → 게시 → 정산·추천 보상을 격리 데이터로 검증한다.

각 단계는 독립 데모가 아니라 하나의 운영 흐름으로 연결되어야 한다. 운영 데이터의 상품 가격이나 모집 공고는 구현을 위해 임의로 공개하지 않는다.
